## 终端报错的原因

部署脚本在 `systemctl start` 返回后立即探测端口。第一次请求发生在监听就绪前，curl 报连接拒绝；旧脚本随后尝试将空响应解析为 JSON，因而打印 `JSONDecodeError` 堆栈。等待循环没有将这次失败判为健康，而是继续重试；后续检查通过后，脚本核对了实际运行程序、配置与保护状态，才输出 `Deployment passed`。

因此本次为**启动等待阶段的探测失败及多余报错输出**，不代表部署失败。现场复查确认目标版本正在运行，无需重复部署或回滚。

## 脚本修正

- curl 失败时不进入 JSON 解析；连接尚未就绪、空响应、非 JSON 响应及非 `ok` 状态均返回探测失败。
- 正常等待阶段安静重试，不输出 curl 连接错误或 Python 堆栈；预检失败和最终等待失败仍给出明确错误。
- 保留等待超时后的失败返回及自动恢复；持续不健康不会被判成成功。
- 同步修正仓库脚本中**未来生成**的回滚脚本。现有 root 私有备份和其部署时生成的回滚脚本保留原样。

修正后 13 项临时目录隔离测试通过，新增覆盖启动延迟后成功、回滚延迟后恢复、空/非法/非对象 JSON、非健康状态，以及预检端口不可用时的清晰错误。真实服务器再次执行了只读 `--check`，没有再次执行 `--apply`、停止服务或修改运行中的二进制。
