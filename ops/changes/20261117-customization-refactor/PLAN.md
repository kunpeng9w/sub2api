# 降低上游合并成本的定制代码重构方案

日期：2026-11-17（Asia/Singapore）。状态：已在 v0.2.21 定制基线上按收益完成收拢；额度包试点已按停止条件撤回，固定出口保持现有实现。实施与同 SHA Actions 验收见 [VERIFICATION.md](VERIFICATION.md)；v0.2.22 留待独立升级。

## 1. 结论与范围

可以开展一次有明确终点的结构重构：继续使用上游的转发、账号用量、监控执行和存储流程，把本项目独有的规则与增强收拢到独立实现，通过少量、可登记的适配点接入。

优先级是减少对上游共享流程的长期改写，其次才是目录整齐。已有的独立服务和文件继续使用；只有能减少共享文件中的定制逻辑、重复实现或调用依赖时，才引入新模块。

本方案以参考聊天 `01a1e7b3-a1a1-70b1-8dd5-058bc9bab622` 的问题为起点。分析基线固定为：

- 上游 `v0.2.21^{commit}`：`10ba8f9b4dc2e6023d4a9879ab77b21841babd10`。
- 当前分支 `codex/monitor-temp-unschedulable`：`0161258af6ca167f5885c145b454d3a982839939`。
- `v0.2.22^{commit}`：`b0fa9f3e6eeab1968a53e1289b69daa4bb40ca2b`，仅用于检查下一次更新的实际重叠，不混入 v0.2.21 定制差异统计，也不表示本方案已经执行升级。

本轮从上述基于 v0.2.21 的定制分支提交开始重构，保留已有定制，不回退到纯上游标签。先完成结构重构及验收，再单独评估 v0.2.22 升级；v0.2.22 在本轮仅作为源码参考和合并演练目标，不合入重构交付分支。

重构期间维持现有功能与请求行为。复用已经存在于当前基线中的同等能力时，须给出替代依据；仅在 v0.2.22 中出现的替代能力登记为后续升级候选，不能据此提前删除当前实现。产品行为变更留到重构验收后的独立工作中决定、提交和验收。

## 3. 先固定需求，再调整实现

| 能力 | 重构期间保留的契约 | 可以调整的实现 |
| --- | --- | --- |
| 代理不回退 | 已绑定代理不可用时阻断；不改绑直连或备用代理；明确的未绑定账号按现有规则处理 | 校验组织方式、客户端包装、辅助函数位置 |
| 代理生命周期 | 到期保留绑定；更新、续期和删除遵守既有事务与调度快照失效规则 | 仓储内的辅助实现与策略入口 |
| 手动监控 | 管理员和获授权用户可执行，复用检测、历史和可用率流程 | handler 组织、执行前后的定制协调代码 |
| 监控权限与并发 | 用户可见范围、账号权限、执行锁、冷却、并发槽及真实请求生命周期保持一致 | 依赖注入、规则接口与共享请求的内部组织 |
| 监控状态 | 全局 5h/7d 判定、耗尽为 failed、暂停与自动检测关闭区分、手动状态 12 小时 | 独立的状态推导函数与展示适配 |
| 额度增强 | 多窗口估算、可信采样时间、历史容量、缺失与显式零值的区别 | 估算实现与页面接入方式 |
| 账号额度查询 | 现有权限边界、出口约束、普通/Spark 账号数据隔离及错误分类 | 查询编排、缓存与上游服务复用方式 |
| 网络状态 | 现有独立监控服务及页面、认证与管理员控制边界 | 少量路由、菜单和 locale 注册代码 |

普通 OpenAI 账号的“额度 API 优先、失败后模型兜底”是可观察的请求策略，会影响是否产生模型请求及额度消耗。它不能作为文件搬迁的附带动作被删除。纯结构重构阶段保留当前策略；如果在升级中采用上游刷新策略，需在独立变更中写明请求行为和对应测试的变化。

同样，过期窗口是否归零、刷新失败是否沿用历史额度推导正常状态，都会影响监控结果，须与目录和接口调整分开验收。

## 4. 目标结构与依赖方向

以下是候选边界，路径按实际收益逐步建立，不要求一次创建全部目录：

```text
backend/internal/
  domain/                         已有共享数据类型
  custom/
    egresspolicy/                 不依赖 service/repository 的出口规则
    quotaestimate/                估算计算、时间有效性与历史容量规则
    monitorpolicy/                状态推导等独有规则
  service/
    account_usage_service.go      保留上游入口与主体职责
    account_egress.go              保留兼容桥接，委托独立规则
    custom_*_adapter.go           连接上游服务和定制规则
  repository/
    custom_*_lifecycle.go          在既有事务中执行定制数据操作
  server/routes/
    custom_*.go                   使用既有认证组注册独有接口

frontend/src/
  custom/
    quota/                        独有类型、显示适配与估算组件
    monitor/                      手动控制、权限展示及状态增强
    client-config/                定制模板数据与生成辅助
  router/                         保留上游路由及守卫
  components/                     保留上游组件，通过小接口接入增强
ops/network-status/               继续维护已有独立网络监控服务
```

依赖约束：

1. `custom` 中的纯规则仅依赖标准库和 `domain` 等底层类型，不反向依赖 `service`、`repository`、Gin 或 Ent。
2. Go 的适配器先留在现有 package，以访问必要的既有类型和内部方法；只有边界稳定后才抽成独立 package。不为搬目录而导出大量上游内部符号。
3. 仓储事务与 Ent 映射继续在 `repository`；service 层依赖小接口，由 Wire 在装配阶段连接实现。
4. 上游原有文件中的接入点要有具体职责、错误处理和回归。字段声明、调用点及必要的池化键仍可能需要保留，不能要求共享文件完全零差异。
5. 当前 `Account`、`Proxy`、`UsageInfo` 和 `UsageProgress` 位于 `service` 包，纯规则模块不能直接引用这些类型。适配层将必要字段转换为最小输入，显式传入当前时间；已有合适的 `domain` 类型可直接复用。不为满足目录布局迁移整个领域模型，也不建立与上游大结构逐字段对应的副本。账号读取、费用查询、缓存、执行锁和持久化继续留在现有协调层。
6. 路径和命名前缀不能作为归属依据。上游本身已有 `custom_admin_*` 等文件，`channel_monitor*` 也大量来自上游；归属按固定基线差异与需求清单确认。

现有插件体系主要面向 `openai.oauth.outbound_transport.v1`，不能直接覆盖多平台代理、OAuth、监控权限和用量编排。本轮采用编译期模块与显式适配，不扩展成通用插件平台。

## 5. 各模块的具体处理

### 5.1 严格出口：统一规则，逐条核实接入覆盖

现有 `ResolveAccountProxyURL` 已经集中了一部分规则。下一步重点是减少各入口承担的策略细节，并保持实际出口完整覆盖。

| 请求路径 | 可利用的边界 | 必须保留的约束 |
| --- | --- | --- |
| 普通 HTTP / TLS 指纹 | `service.HTTPUpstream` 的 `Do`、`DoWithTLS` 与生产 provider | 最终绑定检查、错误映射、响应体关闭、审计和 TLS 行为 |
| 连接池与监控请求 | transport 创建与客户端派生位置 | 路由版本/监控上下文隔离、重定向限制、旧连接回收 |
| WebSocket | dialer、pool acquire 和 lease | 建连及等待后再次校验、路由兼容键、连接复用与每轮审计 |
| OAuth / 配额 / req 客户端 | 各客户端工厂及绑定解析入口 | 尚无账号时的显式代理选择、会话路由固定、账号范围和调用权限 |
| 插件出站 | 插件调用前的宿主边界 | 插件绕过 HTTPUpstream，仍需校验当前绑定并传递审计上下文 |
| 批量图片、轮询与下载 | 已有账号出口 context 与 transport | 后台任务继续使用选定账号线路，取消或脱离请求后不丢路由 |

先评估通过组合方式包装 `HTTPUpstream`，将独立的最终校验与审计移出上游主体；底层池化、重定向或 TLS 阶段需要信息时，保留小的显式接口。不能假定外层 `Do` 包装能覆盖每一跳重定向、TLS 握手和连接池的内部行为。

删除调用方校验前，为每个调用点登记它实际使用的客户端。只有证明同一约束已在共同出口执行，才删掉冗余部分；选路时与排队后使用时的两次校验可能分别防范不同的变更窗口。

代理到期与绑定保持在仓储事务内处理：标记到期、快照失效和 outbox 写入的原子性不变。HTTP 包装不能替代数据库生命周期规则，也不能依靠请求时阻断来允许后台先把绑定改成直连。

### 5.2 用量刷新：保留上游能力，在策略边界做定制

`account_usage_service.go` 是优先收拢对象，但应保留上游函数和文件的自然位置。提取本地新增的编排、缓存状态和增强处理，不把整个上游用量服务复制到另一个目录长期维护。

建议分成三个职责：

- 读取与刷新：尽量调用上游已有的 quota service、模型探测、凭据解析与快照读写。
- 请求策略：明确入口是普通账号页、受限读取、监控还是 passive；决定允许的请求类型、force 与共享任务范围。每条入口只有一个明确的编排实现。
- 结果增强：在得到用量后添加独有的采样、估算与展示字段，避免把增强逻辑散落到各 provider 的解析过程。

如果某项请求策略是必须保留的定制，就将它独立实现并记录接入原因；当前基线已有同等能力时可复用，并验证行为等价。v0.2.22 提供的替代实现只登记到后续升级清单，本轮不提前引入，也不为预计将被替换的旧实现扩展功能。缓存和 singleflight 本身不是业务需求，但替换后仍需满足权限隔离、路由隔离、取消语义和真实执行期限。

账号页面的调用者取消可以停止自己的等待；监控执行槽则需要覆盖实际网络任务和结果保存。复用底层读取能力时明确这两种生命周期，不能为了统一外观而提前释放监控锁。

### 5.3 额度估算：先明确语义，再统一新增增强

当前后端 `quota_estimate.go` 和 `QuotaEstimateView.vue` 已相对独立，应复用；账号页 `openAISevenDayEstimatedTotalCost` 的公式则原本来自上游。

后端的增强估算包含采样截止、本地费用口径、窗口有效性和历史容量，不能仅凭公式相同就认为它与上游账号页 7d 显示完全等价。

实施时：

1. 为本项目的多窗口、剩余额度、采样和历史容量确定单一数据契约，继续由后端产生，前端负责展示。
2. 保持 `UsageProgress`、监控 tier 和现有 JSON 字段兼容；独有 TypeScript 类型可独立声明，再通过小的引用或 re-export 接回。
3. 上游原生 7d 展示若满足需要，保留原实现。若要求账号页与监控采用完全相同的增强估算，单独切换其数据源，并说明过期、无估算和历史容量时的显示变化。
4. 不通过“后端值缺失就无条件重算”掩盖不可用原因，否则会绕过采样有效性规则。

这样能统一需要统一的新增功能，同时控制为重写上游显示而引入的差异。

### 5.4 渠道监控：复用执行链，提取规则与协调

继续使用现有 `RunCheck`、调度器、历史与日聚合、配额抓取、DTO 和基础组件。

可提取的独有部分是：可见权限、手动执行的锁与冷却、账号出口 context、账号调度状态映射、全局额度状态和手动结果有效期。适配器把这些规则接入既有入口；自动执行和手动执行共用实际检测与保存流程。

`monitorDisplayStatus` 与 `monitorQuotaWindowStatus` 的决策输入应明确。展示状态不改写历史样本；状态规则变更影响可用率或告警时，独立记录。保留 `Enabled` 与 `AutoCheckEnabled` 两个不同含义，继续尊重监控 V1/V2 的运行模式门控。

监控查询继续复用账号服务。配额、凭据失效和其他平台余额等含义通过适配映射，不为监控再复制一套 provider 网络查询。

### 5.5 前端与独立功能：按收益整理接入

网络监控后端已经只有独立 gateway 与少量路由调用，是较好的边界；当前无需重写该服务。

随着新增功能增加，可将独有路由、菜单、locale 放在统一的小入口中，主文件只负责合并。合并顺序、用户/管理员可见性、simple mode、feature flag 和路由守卫仍沿用原流程。当前只有少量条目时，不把建立通用注册框架作为重构前置条件。

`UseKeyModal.vue` 中的定制配置适合提成纯模板辅助函数或数据，组件继续负责原有客户端选择与展示。不要复制整个组件维护定制版本。

## 6. 数据库与生成代码

本轮重构优先保持数据库结构、公开 API 路径和已有 JSON 字段不变。

- 已执行的 `249_channel_monitor_manual_access.sql`、`250_channel_monitor_sort_order.sql` 等迁移保持文件名和内容。未来调整只新增迁移。
- 现有监控列和 viewers 关系无需为目录隔离立即迁到新表。这样做会新增数据迁移、查询连接和部署顺序的维护成本。
- Ent schema 中的字段与关系是必要接入，16 个生成文件的差异由 schema 产生；不要手工整理生成代码来追求较小 diff。
- Ent、Wire 和锁文件生成统一交给 GitHub Actions，审查生成补丁后验证最终提交。

## 7. 实施顺序与每批交付

每批提交必须能独立审查和验证，避免同时调整全部出口。

| 批次 | 交付 | 完成条件 |
| --- | --- | --- |
| 1. 固定需求与接入清单 | 每项定制的需求、入口、依赖和既有测试映射；固定源码 SHA | 能区分必须保留的行为、上游能力和可替换实现 |
| 2. 单模块试点，评估后再扩大 | 先验证额度纯计算的包边界和同 package 桥接；保留 API/数据库契约 | 同批更新 CI，实际用例执行记录和收益评估完成；仅在收益成立时扩大抽取 |
| 3. 收拢刷新与监控协调 | 用量查询的策略适配、结果增强、监控权限/状态/生命周期规则 | 共享文件中的定制分支减少，权限与生命周期回归通过 |
| 4. 按出口收拢网络策略 | HTTP/TLS、WS、OAuth/req、插件、后台任务逐类改动 | 每类均有完整覆盖证据，再删除相应调用方冗余 |
| 5. 小规模前端接入整理与维护约束 | 模板/类型/路由等必要入口、汇总逐批 CI 记录与差异报告 | v0.2.21 基础上的最终 SHA 检查通过，完成重构前后对 v0.2.22 的合并演练对比 |

执行顺序固定为：固定 v0.2.21 定制分支基线与现有行为契约 → 单模块结构试点 → 按收益完成各批重构 → 对最终重构 SHA 完成 Actions 验收及 v0.2.22 合并演练对比 → 再单独考虑 v0.2.22 升级。升级对齐不是本轮重构的前置条件。

实际重构起点为第 1 节的定制分支 SHA `0161258af6ca167f5885c145b454d3a982839939`，上游参照为 v0.2.21。如果实施前分支前进，记录新起点并核对新增差异；不得混入 v0.2.22 升级提交。第 3 节逐项补齐现有入口、实现位置和回归映射；基线或契约未完成时，可继续源码盘点和接口设计，不启动刷新编排与出口的批量改动。

### 7.1 首批试点：额度纯计算边界

试点只验证一个小边界，候选为当前 v0.2.21 定制基线中 `quota_estimate.go` 的 `EstimateQuota`；按现有输入输出和行为契约提取。它已相对独立，提取成功本身不能证明降低了上游合并成本。

- 输入保持费用、百分比及 `start/end/sampled/now`，输出复用 `domain.QuotaEstimate`；候选位置为 `custom/quotaestimate`。必要时在 `service` 保留薄桥接，避免扩大调用方改动。
- 必留契约：有效窗口内按现有公式计算；超过 100% 时剩余量不为负；无效窗口、未来或缺失采样、无效数值继续返回既有不可用原因；不改变 JSON 字段和空值语义。
- 费用查询、各窗口采样时间选择、缓存、历史容量读写继续由现有服务协调，不随纯函数搬迁。
- 既有 `TestQuotaEstimateFormulaAndInvalidInputs` 随纯函数迁移；`TestQuotaEstimateAllWindowsAndSampleCutoff` 和 `TestQuotaEstimateKeepsIndependentWindowSampleTimes` 继续覆盖服务接入、原快照不被修改及窗口时间隔离。缺口只补行为断言，不为桥接新增镜像测试。
- 同批调整 `openai-usage-refresh-ci.yml` 与 `channel-monitor-ci.yml` 的 package 范围及相关检查列表，确保新包进入专项回归。通用 `backend-ci.yml` 的全包检查继续保留。

## 8. 验收与后续更新

一次性完成的范围是：独有策略有清晰归属、共享入口有清单、同等能力优先复用上游、远程回归可复现。后续版本仍可能修改接口和行为，需要升级审查。

维护一份定制接入清单，每项至少记录：

- 需求与实际行为。
- 独立实现位置和触及的上游文件/符号。
- 必须接入此处的原因。
- 既有回归与 Actions job；新缺口对应的验收。
- 上游替代条件，以及删除补丁的条件。

后续可在现有 Actions 中生成共享文件差异与接入点报告。先建立基线，再约束新增散落；接口变化导致的漏接不能只靠文件白名单或函数名检索判定。

重构收益用以下指标评估，排除运维记录、测试和生成文件后分别报告：

1. 修改的上游生产源码文件与定制差异行数。
2. 上游共享函数中保留的定制分支和适配调用点。
3. 独有行为的实现来源，以及实际请求路径的覆盖完整性。
4. 同一目标标签在重构前后的文本合并结果、双方共同修改文件的语义审查结果。

本轮合并演练固定目标为第 1 节记录的 v0.2.22 提交。分别以重构起点和最终重构提交为候选，记录双方 SHA、目标提交 SHA 与各自 merge-base；两个候选均保留相同的上游 v0.2.21 基础，且均未合入 v0.2.22。使用相同工具、参数和统计口径比较，不能直接将初稿逐文件 `git merge-file` 的结果与另一种算法结果比较。演练在临时目录或隔离 checkout 中进行，结果不合回重构交付分支。

除文本冲突外，还需审查自动合并后的适配调用、行为契约和测试接入；冲突减少不能替代语义审查。演练中发现的 v0.2.22 行为变化登记到后续升级清单，不据此修改当前重构的验收语义。重构验收通过不代表 v0.2.22 升级已通过；正式升级仍需独立完成远程检查。

停止条件：如果一次抽取只移动代码、增加桥接或类型转换，没有减少共享函数中的定制逻辑、重复实现或调用依赖，则不扩大该抽取。若需大量导出上游内部符号、复制领域结构或破坏现有生命周期才能继续，重新选择边界。各模块分别判断收益，不要求完成全部候选目录。

不预先承诺“只改几个文件”或“以后零冲突”；通过实际差异和演练验证收益。

全部编译、测试、Lint、类型检查、生成和构建在 GitHub Actions 执行：

| 检查 | 复用工作流与主要场景 |
