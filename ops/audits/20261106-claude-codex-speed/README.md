# Claude 低 TPS 与 Codex、服务器带宽对照

分析日期：2026-11-06；所有展示时间均为 Asia/Singapore（UTC+8）。只读排查，没有压测、上游探活、服务重启或配置变更。用户已有的 Nginx 配置未提交改动保持原样。

## 结论

**存在同时段变慢的证据，但没有找到“Codex 占满本机公网带宽，导致 Claude 变慢”的充分证据。** 更直接的观测是请求首响应等待变长，Claude 首响应后输出速率变化相对较小。共同原因仍可能位于服务器至代理/上游的链路、代理节点、请求上传、上游排队或模型处理阶段，现有记录无法区分。

用户确认服务器峰值公网带宽为 **200 Mbps**。这是用户提供的规格，未通过云控制台独立核实；峰值也不等于持续保证带宽。慢窗口的 eth0 收发各平均约 0.66 Mbps，约峰值的 0.33%，无法据此认定服务器总带宽耗尽。

## 数据与口径

- 固定查询范围：2026-11-05 19:00 至 2026-11-06 23:50，不含结束时刻。现存 Claude 数据始于 11-05 19:30，覆盖 363 条 Claude 请求；Codex 仅选同一范围内 OpenAI 平台的文本调用，并排除无有效输出/耗时的记录。
- 请求数据来自 PostgreSQL `usage_logs`；CPU、队列来自 `ops_system_metrics`；网络来自 `/var/log/sysstat/sa05`、`sa06` 的 eth0；响应字节来自 Nginx `sub2api.access.log*`。
- 按应用源码 `queryOutputTPS` 的口径：单请求 TPS = `output_tokens * 1000 / duration_ms`，窗口平均为单请求 TPS 的算术平均。此次有效样本均为常规同步/流式/WebSocket 文本请求，不包含图像请求。
- 请求按完成后用量记录时间 `created_at` 分桶。主比较使用十分钟窗口，且要求至少 3 条有效 Claude 请求；共 32 个窗口，另 10 个稀疏窗口保留在 CSV，未纳入分组统计。
- 定义 Claude 慢窗口为上述平均 TPS <80；为便于核对，将 Codex <10 TPS 定义为“很慢”。这只是本次分析阈值，不是通用模型性能标准。
- 日志 `first_token_ms` 以下简称 TTFT。Claude 源码实际上可在首条有效 SSE data 事件时记录，因此它更接近**首响应事件等待**，不保证是第一字可见文本。扣除 TTFT 后速率采用 `Σ输出 tokens / Σ(duration_ms-first_token_ms)`，避免极短输出阶段使逐请求比率平均失真；该值也不是精确的逐 token 解码速度。
- 网卡采样一般每十分钟一次，按实际采样区间与分析窗口重叠秒数加权。单位为 Mbps，按 sysstat 的 KiB/s ×1024×8/1,000,000 转换。eth0 包括整机全部流量，不能全部归给 Codex；收发方向分别比较，不相加认定占满。

同模型核对也能观察到变化：`gpt-6.1-terra` 在慢/正常窗口分别 83/114 条，平均 TPS 4.26/17.77，平均 TTFT 80.64/7.05 秒；`gpt-6.1-sol` 则为 296/136 条，平均 TPS 20.21/21.32，TTFT 23.07/7.39 秒。Codex 的变慢程度并不一致，汇总结果也受模型、推理与输出长度影响。单独看 Claude Opus，慢/正常窗口平均 TPS 为 47.70/84.04，TTFT 11.47/1.54 秒，扣除 TTFT 后速率 103.48/110.25 TPS，变化方向与总体一致。

## 补充观察与限制

- 慢时段并无 CPU 持续饱和迹象：15 点、19–22 点的分钟样本 CPU 平均约 3.9%–5.3%；应用记录的并发等待队列最大为 0。队列指标本身可能不覆盖所有等待阶段，不能据此排除上游排队或系统短时异常。
- 15 点有 12 条 OpenAI `upstream_error` 和 1 条 `api_error`，包括 HTTP/2 connection lost、TLS handshake timeout、PROTOCOL_ERROR，支持“链路/上游异常值得继续查”的方向，但不足以定位故障层或证明带宽争用。
- 现有账号配置显示 Claude 与部分 Codex 使用同一代理 ID 1；Codex 的其他代理也出现过明显 TTFT 增长。账号当前代理绑定不等于每条历史请求的真实路由，不能把当前配置当作历史出口证明。
- Nginx 有大请求体写入临时文件的日志；Claude 部分慢时段上下文更大，例如 14 点平均约 15.1 万 tokens、15 点约 25.5 万。上下文与处理时延是潜在混杂因素，token 数不能替代网络字节数，缓存 token 也不能直接当作省掉的传输量。
- Nginx 现有格式只记录响应体字节和请求总耗时，**没有 request_length、逐请求上游发送字节、逐秒流量**。WebSocket 的响应字节在连接结束时整笔记录，一个连接可能承载多个模型调用，无法精确按分钟或调用分摊 Codex 流量。不能用 token 数或完成时刻响应字节反推瞬时带宽占用。
- sysstat 没有保存 TCP 重传活动，且十分钟均值会掩盖短时峰值；缺少云侧限速/丢包、代理带宽、逐秒 RTT 和分段延时。峰值 200 Mbps 也不直接证明服务器至各代理的可用带宽。**现有证据不支持服务器总带宽耗尽，但不能排除短时拥塞、运营商路径或代理节点限速。**

若继续验证带宽因果，最有价值的是对齐云侧秒级公网流量/限速/丢包、各代理链路的 RTT/重传，以及请求上传、首响应、输出阶段耗时。此次只分析已有记录，没有安装采集器或改日志配置。
