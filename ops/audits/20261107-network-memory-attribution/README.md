# 网络与内存停顿同步归因

时间：2026-11-07 09:07–09:09，Asia/Singapore。

## 结论

本轮在内存压力很低的窗口仍复现 1 MiB 上传需 7–9 秒及大量 TCP 重传，直接公网、代理 1、代理 2 均受影响。结合此前生产请求大体积上传耗时，主要可行动瓶颈是服务器到公网 TCP 对端的传输路径；不是仅凭模型推理或 Sub2API 实现才能出现的问题。不能据此定位云侧、运营商、代理接入端的具体丢包点，也不能证明所有路径同一根因。

## 探测方法

复用已有 probe.py，新增每个请求窗口的 Sub2API cgroup PSI 累计差、整机换入换出字节差及服务 major fault 差。6 次串行新建连接，HTTP/1.1，向 Cloudflare 官方测速上传端点发送 1 MiB 合成 x，均完整上传并 HTTP 200，无响应正文。未使用模型凭据或用户内容，未发起模型调用，代理认证仅在进程内与 curl stdin 中使用。每个请求 35 秒时限，ss 每 0.5 秒仅采该 curl 的 socket，不记录地址或认证。

PSI 窗口包含启动/收尾采样开销，略长于 curl 请求；服务 PSI 是同期生产 Sub2API 的指标，探测 curl 不属于该 cgroup。不能把服务 PSI 当成 curl 停顿。

重传量是连接期间采样的最大累计值，可能漏掉最后一次采样后的重传，不是 IP 丢包率。直连握手仅约 44 ms，代理约 1.2 s；主体等待在握手之后。代理 2 第二轮本地 upload_done 约 2.51 s，首响应约 8.66 s，仍有发送排队和重传；本地写完不代表远端已收到全部数据，不能把其后等待全部归为上游处理。

本机 eth0 接口 errors/dropped 和 fq_codel dropped/overlimits/requeues 均为 0；这不能排除虚拟网卡之外的云宿主机/网络丢弃。当前数据优先支持共同出口方向排查，但确定云侧限速或线路故障需要云平台秒级丢弃/限速指标、代理接入端观测或另一服务器同目标对照。

## 内存延迟的定量边界

对已有 socket-samples.json 的 08:40:10.324842–08:40:53.879328 窗口重新计算累计值差：

- 窗口 43.554486 s；整机 memory some 6.291489 s（14.45%），memory full 5.764609 s（13.24%）。
- IO some 9.698540 s（22.27%），IO full 8.699331 s（19.97%）。内存与 IO 停顿可重叠，不可相加。
- 这量化的是资源压力状态持续时间，不是每条请求额外延迟，也不是纯 Swap 读盘时间。some 是至少部分任务停顿，full 是所有非空闲任务同时停顿；full 不是单请求延迟上界。
- 本轮整机 memory some 仅 1.7–58.9 ms、full 1.6–49.3 ms；服务 memory some 0–2.3 ms。换入最多约 9.8 MiB 的窗口仍只有 13.9 ms 整机 memory some，说明换入量或 Swap 存量不能直接换算延迟。
- 可以确认历史高压力窗口出现秒级资源停顿，而本轮网络异常在低内存压力下独立存在。不能将总请求耗时减 PSI 就称作纯网络耗时，也不能给历史 60 秒慢请求分配精确的 Swap 占比。

精确 Swap-in 等待可由 Linux taskstats 的 delay accounting 测量，当前 kernel.task_delayacct=0，历史计数不可追补。官方文档说明启用后只对新启动任务提供数据。本次未改内核参数或重启业务。未来在维护窗口启用并随正常服务重启生效，可采 swapin/reclaim/CPU/IO 的线程级时间差；多线程累计时间仍不能直接作为单请求墙钟延迟，须和请求阶段/线程调度轨迹关联。Go goroutine 会迁移线程，进一步归因需请求追踪与调度观测。
