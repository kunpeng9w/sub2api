# 代理链路合成请求定位（2026-11-07，Asia/Singapore）

## 结论

绕过 Nginx、Sub2API、模型服务和业务请求内容后，独立 curl 连接仍能复现明显的 TCP 重传、发送积压和慢上传。问题不限于代理 2：生产绑定的代理 1、2、4，以及不配置代理的公网直连，均出现异常。**优先排查本机共同公网发送路径（虚拟网卡/云侧出口策略、公共路由），不能把根因限定为某个代理节点、模型推理或 Go 请求实现。**

这不是云侧限速已经得到证明。现有观测只能确认本机至 TCP 对端的传输受阻，不能在云宿主机、云侧限速/丢弃、运营商路径、对端接入之间定位丢包点；也没有代理服务端指标。直连异常扩大了故障范围，但不能证明所有路径具有同一个根因。

## 方法

按用户本轮明确要求，在运行服务器进行有限的合成网络请求探测。单次发送 1 MiB 的重复字符 x，不含用户输入、业务请求内容、API key 或模型账号凭据。代理认证仅用于已有代理，经 curl stdin 配置传入；不落盘，不输出原始 verbose 日志。所有请求串行、每次新连接，连接上限 10 秒、总时限 35 秒。未切换业务账号出口，未改线上服务配置、TCP 参数或重启服务。

每 0.5 秒通过 ss 只保留该 curl PID 的 TCP 指标，不保存代理 IP/认证信息。PSI 为整机累计 stall 时间差，包含探测控制与采样开销，并非 curl 自身停顿时间。结果是一次短时诊断，非 SLA、独立丢包率或长期基准。

文件：probe.py 为可复用探测脚本（运行会实际发送合成请求）；results.jsonl 为脱敏逐请求数据；interface.json 为 10 秒网卡样本。

httpbingo.org/post 对本次 1 MiB 数据返回 HTTP 400，且提前结束上传。相关 round=2 的六条记录保留用于审计，**不作为有效完整上传性能样本**。

|---|---|---:|---:|---|---:|

该端点回显约 1 MiB 响应，接收响应阶段也耗时明显；三条超时不能表述为完整请求成功。仅比较完整上传后的首响应时刻，可见代理 2 的 H1/H2 都约 13 秒。单次、串行、新连接对照只能说明关闭 H2 没有消除本次异常，不能排除生产 H2 并发复用的额外影响。

尤其是代理 2 H1：curl 在约 2.59 秒报告 upload_done，但之后依然有发送积压，首响应在约 12.94 秒。这说明应用层 WroteRequest/upload_done 后的等待还可能包含内核缓冲数据发送、重传与确认，不能全部归给上游推理。
